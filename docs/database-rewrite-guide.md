# AMOS Database Rewrite Guide

本文用于指导后续通过 LLM 逐步开发 AMOS 后端数据库与业务模块。核心原则是：**PostgreSQL 是目标生产数据库，H2 是快速验证数据库，Flyway 是唯一业务表结构来源**。

- 后端工程：`/Users/zhenghai/Code/fde-training-lab/prototypes/amos-server`
- 数据库迁移目录：`amos-app/src/main/resources/db/migration`
- PostgreSQL 本地说明：`docs/postgres-setup.md`
- 总体转写计划：`docs/amos-rewrite-plan.md`
- API 契约：`docs/api-contract.md`

## 1. 当前判断

现在已经可以开始创建 PostgreSQL 相关脚本，而且是合适时机。

原因：

- 后端已经引入 Flyway，并已有 `V1__init.sql`。
- 后端已经有 H2 内存数据库，便于快速启动和测试。
- 后端已经预留 PostgreSQL profile，具备切换到真实 PostgreSQL 的基础。
- 当前业务表还少，越早统一迁移规范，后续 AMOS 大量业务表的返工越少。

但不要单独维护一套 PostgreSQL 业务建表脚本。业务表结构必须继续通过 Flyway 管理。

## 2. 数据库脚本分工

### 2.1 数据库初始化脚本

用途：本机或服务器首次创建 PostgreSQL 数据库和账号。

建议位置：

```text
scripts/postgres/00_create_database.sql
```

只允许包含：

- `CREATE DATABASE`
- `CREATE USER`
- `GRANT`
- schema 权限配置

不要包含：

- AMOS 业务表
- 业务索引
- 业务种子数据
- 字典表数据

这些业务内容必须进入 Flyway migration。

### 2.2 Flyway 业务迁移脚本

用途：创建和演进 AMOS 业务表结构。

位置：

```text
amos-app/src/main/resources/db/migration
```

命名：

```text
V1__init.sql
V2__component_type_children.sql
V3__system_scope.sql
V4__functions.sql
```

要求：

- 版本号只能递增。
- 一个业务切片对应一个或少数几个 migration。
- 已经提交并在环境中执行过的 migration 不要随意改历史内容。
- 如果需要改已执行结构，应新增下一个版本 migration。
- H2 和 PostgreSQL 尽量共用同一套 migration。

### 2.3 本地开发说明文档

用途：说明如何创建 PostgreSQL、启动后端、验证 Flyway。

位置：

```text
docs/postgres-setup.md
```

这类文档只描述操作，不定义业务表结构。

## 3. 必须遵守的原则

### 3.1 Flyway 是唯一业务结构来源

后续开发中，任何业务表、字段、索引、约束、种子数据，都应该进入 Flyway migration。

禁止：

- 通过数据库 GUI 手工创建业务表。
- 单独维护 `schema-postgres.sql` 和 `schema-h2.sql` 两套业务脚本。
- 依赖 `spring.jpa.hibernate.ddl-auto=update` 自动改表。
- 在 Java 实体里改字段后不补 migration。

### 3.2 PostgreSQL 优先，H2 兼容

建模时以 PostgreSQL 为最终目标，但迁移脚本要尽量保持 H2 可跑。

推荐写法：

```sql
id bigint generated by default as identity primary key
```

优先避免：

```sql
bigserial
serial
gen_random_uuid()
do $$ ... $$
```

常用类型建议：

| 场景 | 推荐类型 |
| --- | --- |
| 主键 | `bigint generated by default as identity primary key` |
| 编码/编号 | `varchar(50)` 或 `varchar(100)` |
| 名称 | `varchar(255)` |
| 长说明 | `text` 或 `varchar(1000)` |
| 金额 | `numeric(18,2)` |
| 数量 | `numeric(18,4)` |
| 日期时间 | `timestamp` |
| 日期 | `date` |
| 状态 | `varchar(50)`，Java 侧用 enum 管控 |
| 布尔 | `boolean` |

### 3.3 不要提前过度拆微服务

当前推荐继续采用模块化单体。

包结构可以逐步演进为：

```text
com.neusoft.amos
  common
  system
  register
  maintenance
  stock
  purchase
  financial
  workflow
  audit
```

复杂业务模块内部建议采用：

```text
module
  api
  application
  domain
  infra
```

### 3.4 业务动作不能只做 CRUD

AMOS 的核心价值在业务状态流转。后续每个模块都要区分：

- 简单主数据：可以先用 CRUD。
- 业务流程：必须使用明确 command endpoint。

例如 Components：

```text
POST /api/maintenance/components/{id}/install
POST /api/maintenance/components/{id}/remove
POST /api/maintenance/components/{id}/change-status
```

而不是只暴露：

```text
PUT /api/maintenance/components/{id}
```

## 5. 每次让 LLM 开发数据库模块时的标准流程

后续每个数据库切片，都按这个顺序执行。

### 5.1 先分析

要求 LLM 先读取：

- 对应前端页面。
- 对应前端 service。
- `src/mock/index.js` 中对应 mock 数据。
- `docs/api-contract.md`。
- `docs/data-model.md`。
- `docs/manual-mapping.md` 中对应手册章节。
- 现有 Java 实体、Repository、Controller。
- 现有 Flyway migrations。

输出：

- 当前字段清单。
- 当前页面动作。
- 当前 Mock 业务规则。
- 需要新增的表。
- 需要新增的 API。
- 需要新增的测试。

### 5.2 再设计

要求 LLM 先给出设计，不要直接乱写代码。

设计内容：

- 表结构。
- 主键和唯一约束。
- 外键关系。
- 索引。
- 状态枚举。
- 业务动作 endpoint。
- DTO 字段。
- 和前端字段的映射。

### 5.3 再实现

实现内容：

- 新增 Flyway migration。
- 新增或更新 Entity。
- 新增 Repository。
- 新增 Service。
- 新增 Controller。
- 新增 DTO。
- 新增测试。
- 前端 service 接 API。

### 5.4 最后验证

至少验证：

- H2 启动成功。
- PostgreSQL profile 启动成功。
- Flyway migration 成功。
- 后端测试通过。
- 前端 build 通过。
- 对应页面能完成核心操作。

## 6. 每个 Migration 的检查清单

新增 migration 前检查：

- 版本号是否递增。
- 文件名是否符合 `V{n}__{description}.sql`。
- 是否会破坏 H2 兼容。
- 是否重复创建已有表或字段。
- 是否需要索引。
- 是否需要唯一约束。
- 是否需要外键。
- 是否需要初始化种子数据。
- 是否有幂等风险。

新增 migration 后检查：

- H2 能跑。
- PostgreSQL 能跑。
- `flyway_schema_history` 有记录。
- Java 实体字段与表字段一致。
- API 测试覆盖新增表。

## 7. PostgreSQL 初始化脚本建议

如果尚未创建，可以新增：

```text
scripts/postgres/00_create_database.sql
```

建议内容：

```sql
create database amos;

create user amos_app with password 'amos_app';

grant all privileges on database amos to amos_app;
```

实际本机环境可能需要根据 PostgreSQL 版本补充 schema 授权：

```sql
grant usage, create on schema public to amos_app;
alter default privileges in schema public grant all on tables to amos_app;
alter default privileges in schema public grant all on sequences to amos_app;
```

注意：这个脚本只负责创建库和用户，不负责建 AMOS 业务表。
